## 1. Executive Summary

Following the completion of Phase 6.1 (which established a verified server discovery service and an asynchronous Mercury UDP transport prototype with 72 passing automated tests), Phase 6.1.1 conducts a deep-dive compatibility audit to determine whether an original, unmodified iOS client can connect to our private server infrastructure.

By performing static analysis, Mach-O disassembly, and cryptographic inspection on `RoS-Legacy-iOS.ipa`, this audit establishes the precise technical boundaries between working code, confirmed protocol facts, architectural missing pieces, and cryptographic hard blockers:

1. **Mercury Interface Architecture Confirmed**: Disassembly of `extracted/Payload/client.app/client` confirms the exact structure of `LoginInterface` (VA `0x1008cde0c`), `BaseAppExtInterface` (VA `0x1008cde84`), and `ClientInterface` (VA `0x1008ce144`). Mercury datagram footer order, 16-bit flag bitmasks, and 2-byte variable length prefixes implemented in Phase 6.1 match the client's native BigWorld implementation.
2. **Cryptographic Hard Blocker Identified (LoginApp RSA & Blowfish)**: The iOS client binary embeds NetEase's 1024-bit RSA public key (`entities\loginapp.pubkey` in `res/entities.npk`, Entry ID `0xd9aee0dd`). Disassembly of `ServerConnection::logOnBegin` (VA `0x1008abe00`) confirms that if this file is missing or fails to initialize, the client immediately aborts with error `0x701` (`PUBLIC_KEY_LOOKUP_FAILED`). During logon, the client generates a random symmetric Blowfish session key, encrypts it under NetEase's RSA public key, and subsequently activates `neox::bwclient::Mercury::EncryptionFilter` on the BaseApp channel. Because only NetEase possesses the matching private key, a private server cannot decrypt this session key from an unmodified IPA.
3. **Discovery & TLS Limitations**: iOS `Info.plist` configures `NSAppTransportSecurity` with `NSAllowsArbitraryLoads = True`, confirming that Apple's OS-level ATS does not prohibit plaintext HTTP. However, the game client scripts explicitly target `https://as-h45na.easebar.com:50010`. Redirecting this endpoint via DNS on an unmodified iOS device will fail TLS verification unless a custom Root Certificate Authority (CA) profile is installed and trusted in iOS Settings, or traffic is routed through a local proxy.
4. **Viability Verdict**:
   - **Strictly unmodified iOS client on stock iOS without device profiles**: **NOT VIABLE** due to the dual hard blockers of the proprietary 1024-bit RSA public key and TLS certificate domain validation.
   - **Sideloaded / Resigned IPA (via AltStore, TrollStore, or Sideloadly) with Key Swap**: **100% VIABLE**. Swapping `entities\loginapp.pubkey` with the private server's RSA public key requires zero Mach-O executable modification and allows clean-room decryption of the client's Blowfish key, enabling full bidirectional Mercury communication.
5. **Regression & Safety**: All 72 existing automated unit and integration tests remain 100% passing. No IPA modifications, binary patching, database migrations, or public network connections were made.

### 3.2 Mercury Header & Footer Layout

Disassembly of `neox::bwclient::Mercury::Nub::processFilteredPacket` (VA `0x100922894`) establishes the exact datagram layout:

```
+------------------------------------------------------------------------------------+
| Bytes 0..1 | Bytes 2..(End - FooterLen) |                 End of Datagram          |
| uint16     | Bundled Mercury Messages   |                (Parsed Backwards)        |
| Flags      | [MsgID:1B][Len:0/2B][Data] | [Fragment][Channel][ACKs][Seq][Checksum] |
+------------------------------------------------------------------------------------+
```

1. **Header (Offset 0..1)**: 16-bit little-endian integer. Packets with `flags >= 0x0400` are immediately dropped as malformed.
   - `FLAG_HAS_REQUESTS = 0x0001`
   - `FLAG_HAS_ACKS     = 0x0004`
   - `FLAG_ON_CHANNEL   = 0x0008`
   - `FLAG_IS_RELIABLE  = 0x0010`
   - `FLAG_IS_FRAGMENT  = 0x0020`
   - `FLAG_CREATE_CHAN  = 0x0040`
   - `FLAG_HAS_CHECKSUM = 0x0100`
2. **Reverse Footer Unpacking Order (from tail backwards)**:
   - **Checksum (4 bytes)**: Present if `flags & 0x0100`. Verified as little-endian uint32.
   - **Sequence Number (4 bytes)**: Present if `flags & 0x0010`. Monotonically increasing uint32 packet sequence.
   - **Cumulative/Selective ACKs**: Present if `flags & 0x0004`. Format: 1-byte count $N$ followed by $N \times 4$ bytes of uint32 sequence numbers.
   - **Channel Metadata (8 bytes)**: Present if `flags & 0x0008`. Format: 4-byte Channel ID + 4-byte Channel Version.
   - **Fragment Metadata (4 bytes)**: Present if `flags & 0x0020`. Format: 2-byte `firstSeq` + 2-byte `lastSeq`.

The Phase 6.1 `MercuryPacket` implementation in `ros-private-server/mercury/packet.py` strictly adheres to this unpacking sequence.

### 4.2 Blowfish Symmetric Cipher Activation

When `PublicKeyCipher::setKey` succeeds, the client does not merely encrypt credentials—it establishes symmetric stream encryption for all subsequent Mercury communication:
1. Strings in Mach-O at `0x1030a3c51` (`PublicKeyCipher::setKey: Loaded %d-bit %s key`) confirm RSA initialization.
2. The client generates a random Blowfish symmetric key (`neox::bwclient::Mercury::EncryptionFilter`, mangled symbol `_Blowfish`, `EncryptionFilter::initKey`, `EncryptionFilter::encrypt`, `EncryptionFilter::decrypt`).
3. The generated Blowfish key is packed inside the RSA-encrypted `LoginInterface::login` datagram payload.
4. When the client establishes the BaseApp channel, it activates `neox::bwclient::Mercury::EncryptionFilter` using this Blowfish key.

## 5. Discovery & TLS Limitations

### 5.1 iOS App Transport Security (ATS) Audit

Inspection of `Payload/client.app/Info.plist` yields:
```python
{
    'NSAppTransportSecurity': {
        'NSAllowsArbitraryLoads': True
    }
}
```
- **Finding**: NetEase explicitly disabled Apple's App Transport Security restrictions by setting `NSAllowsArbitraryLoads = True`.
- **Significance**: The iOS operating system does **not** enforce HTTPS or block plaintext HTTP traffic from this application.

### 5.2 Client-Side URL Hardcoding & Port 50010

Despite ATS being disabled, the game scripts (`patch/extconfigs.py.raw` and `common/serverlist_utils.py.raw`) construct the discovery URL as:
```python
f"https://{access_server}:50010/server_list_ios.txt"
```
where `access_server` defaults to `as-h45na.easebar.com`.

### 5.3 TLS Trust Chain Barrier on Physical Devices

1. **DNS Redirection**: If a private server environment redirects `as-h45na.easebar.com` to a local IP via local DNS (e.g. Pi-hole or router `dnsmasq`), the client attempts an HTTPS handshake with `port 50010`.
2. **Certificate Validation**: The underlying HTTP client (cURL / Apple CFNetwork) validates the server's TLS certificate against the iOS Trust Store.
3. **Domain Barrier**: Because `easebar.com` is owned by NetEase, publicly trusted CAs (such as Let's Encrypt) will not issue certificates for this domain to third parties.
4. **Resolution Requirements**:
   - On a physical iOS device, an administrator must generate a private Root CA, issue a certificate for `as-h45na.easebar.com`, install the `.mobileconfig` profile on the iOS device, and enable full trust in `Settings -> General -> About -> Certificate Trust Settings`.
   - Alternatively, traffic can be routed through an HTTP/HTTPS forward proxy (mitmproxy, Charles, or Shadowrocket) running a trusted local MITM certificate.

## 7. Realism Verdict: Can an Unmodified iOS Client Connect?

Based on assembly disassembly, cryptographic facts, and network security testing, the compatibility verdict is:

```
+-----------------------------------------------------------------------------------------+
| Deployment Target                            | Compatibility Verdict                    |
+----------------------------------------------+------------------------------------------+
| Stock iOS + Strictly Unmodified IPA          | NOT SUPPORTED (Cryptographically Blocked)|
| Stock iOS + Device Profiles / Local Proxy    | PARTIALLY BLOCKED (Blocked at Blowfish)  |
| Sideloaded IPA with Key Swap (AltStore etc.) | FULLY VIABLE AND SUPPORTED               |
+----------------------------------------------+------------------------------------------+
```

### Detailed Justification

1. **Strictly Unmodified IPA on Stock iOS**: **NOT SUPPORTED**.
   - NetEase's 1024-bit RSA private key is unknown and unrecoverable.
   - The client binary demands `entities\loginapp.pubkey` and refuses to connect without it (`0x701 PUBLIC_KEY_LOOKUP_FAILED`).
   - The client encrypts a randomly generated symmetric Blowfish key with this RSA key. Without knowing the Blowfish key, the private server cannot decipher incoming BaseApp UDP traffic.
2. **Sideloaded / Re-signed IPA (Key Swap Only)**: **FULLY VIABLE**.
   - Replacing `entities\loginapp.pubkey` inside the IPA package with our private server's 1024-bit RSA public key requires **zero modifications to the Mach-O binary code**.
   - The game client loads our public key without error, encrypts the Blowfish key, and sends it to our server.
   - Our server decrypts the payload using our private key, instantiates `EncryptionFilter`, and establishes bidirectional, authenticated communication.
   - The discovery URL can either be resolved via local DNS + CA profile, or configured directly in the unpacked script files.
