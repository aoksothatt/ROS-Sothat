# 6. Stage C — Atomic diamond management

This is one of the most important parts of P05.

Administrators must be able to grant or deduct diamonds safely.

## C1. Suggested endpoints

```http
POST /api/v1/admin/players/{player_id}/diamonds/grant
POST /api/v1/admin/players/{player_id}/diamonds/deduct
GET  /api/v1/admin/players/{player_id}/diamonds/history
```

Adapt the paths if the existing API convention requires it.

## C2. Request validation

A mutation request should contain:

```json
{
  "amount": 100,
  "reason": "Compensation for a reported issue",
  "idempotency_key": "unique-operation-identifier"
}
```

Requirements:

- Amount must be a positive integer.
- Reject zero.
- Reject negative input amounts.
- Set a reasonable maximum operation amount based on the existing game's data model.
- Reason must be non-empty and length-limited.
- Reject invalid player IDs.
- Never accept the resulting balance from the client.
- Never accept the administrator ID from the client.
- Administrator identity must come from the authenticated server-side principal.
- Validate idempotency keys and prevent replayed operations.

## C3. Atomicity

The diamond balance and ledger must be updated in the same database transaction.

Conceptual operation:

```text
BEGIN TRANSACTION

1. Authenticate administrator.
2. Verify target player exists.
3. Lock or safely serialize access to the target character balance.
4. Validate current balance.
5. Calculate new balance on the server.
6. Prevent negative balances.
7. Update character diamond balance.
8. Insert immutable diamond transaction record.
9. Insert administrator audit record.
10. Commit.

If any step fails:
ROLLBACK EVERYTHING.
```

Use a database-appropriate concurrency strategy.

Examples include:

- Row-level locking where supported.
- Conditional atomic updates.
- Optimistic version checks.
- Other appropriate SQLAlchemy/database mechanisms.

Do not assume SQLite locking behavior is identical to PostgreSQL.

## C4. Ledger requirements

Every successful operation must record:

- Unique transaction ID.
- Target character/player.
- Operation type: grant or deduction.
- Amount.
- Balance before.
- Balance after.
- Administrator actor.
- Reason.
- Timestamp.
- Idempotency key or equivalent operation reference.

Never edit or delete previous transaction records to hide an operation.

If a correction is needed, create a new compensating transaction.

## C5. Idempotency

A retry must not grant or deduct diamonds twice.

Requirements:

- Same idempotency key and same operation: return the original operation result.
- Same key with conflicting request data: reject with a conflict response.
- Concurrent duplicate requests must not create duplicate transactions.
- Use a database uniqueness constraint where appropriate.
- Do not rely only on an in-memory dictionary.

## C6. Balance validation

Test:

- Granting diamonds.
- Deducting diamonds.
- Deducting exactly the current balance.
- Attempting to deduct more than the current balance.
- Zero amount.
- Negative amount.
- Extremely large amount.
- Missing player.
- Invalid administrator.
- Duplicate request.
- Concurrent requests.
- Database failure during ledger insertion.
- Database failure during audit insertion.

If ledger insertion or audit insertion fails, the balance must remain unchanged.

**Never allow a successful balance update without its matching ledger and audit records.**

# 16. Important distinction — database economy vs actual game economy

ROS Sothat has two separate layers:

**Layer 1 — Private server database**

```text
Admin Dashboard
      |
      v
Secure Admin API
      |
      v
Database
      |
      +-- Character diamond balance
      +-- Diamond transaction ledger
      +-- Inventory
      +-- Administrator audit logs
```

**Layer 2 — Original iOS game client**

```text
Private Game Server
      |
      v
BaseApp / Mercury protocol
      |
      v
Original iOS game client
      |
      v
Visible in-game diamonds and inventory
```

P05 implements and secures Layer 1.

It does not complete Layer 2.

Therefore:

- Do not claim diamonds appear in the original game client.
- Do not claim inventory changes synchronize with the game.
- Do not claim original-client compatibility.
- Document the future integration requirements.
- Preserve the original IPA.
